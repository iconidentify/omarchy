# Session lock recovery

Omarchy records lock intent and a fresh generation in `~/.local/state/omarchy/session-guard/locked` before asking the compositor to lock. The state directory and each ancestor up to HOME are synced too. Password or fingerprint authentication first validates and syncs that generation without deleting intent. Only then does the protocol unlock; cleanup follows that completed unlock. A failed preparation leaves the existing protocol lock and intent in place. Cleanup from an earlier generation cannot remove a new lock, including after a shell restart. A failed cleanup may require authentication at the next login.

The Omarchy UWSM session starts `omarchy-guarded-hyprland.desktop`. Existing `wayland-wm@hyprland.desktop.service` logins receive a late service override too: systemd starts `uwsm aux exec`, which executes the guard, which starts `/usr/bin/Hyprland`. UWSM remains a direct child of the user manager, as its auxiliary API requires. Both paths select the compositor itself, without a nested `start-hyprland` restart loop. The supervisor holds a single-compositor lease and checks intent before executing Hyprland. A crash while locked returns to the greeter. Another compositor is never started and then locked after drawing the desktop. The marker survives reboot, so a subsequent autologin cannot clear it. An authenticated SDDM login clears it through the `sddm` PAM open-session hook. The `sddm-autologin` stack has no such hook, and SDDM automatic relogin is disabled.

Deploy the matching runtime and settings packages together, with a new shared package version and identical source pins so the runtime's exact-version settings dependency forces a paired upgrade. Settings must install both desktop entries and `/etc/sddm.conf.d/90-session-lock-recovery.conf`; runtime must install the helper and its Python implementation and depend on Python. Run `sudo python3 -I /usr/share/omarchy/shell/session-guard-install.py` only after those assets exist. Setup checks their binding and the effective SDDM relogin policy before changing PAM and can be repeated. New installs run the same setup through `install/login/all.sh`; updates run it through the paired post-transaction hook. Do not start a new session during a split runtime/settings upgrade.

The authenticated hook belongs only in `/etc/pam.d/sddm`, after the existing session stack. Never add it to `sddm-autologin`, a greeter stack or an unconditional startup command. A local `/etc/sddm.conf` can override package drop-ins; setup rejects an effective relogin policy other than `false`. HOME and the state namespace must be owned, without symlink components or group/other write access. Keep custom compositor entry points and custom UWSM command arguments out of this profile until they execute the same supervisor.

An already-running unguarded launcher cannot be wrapped by a package upgrade or daemon reload. End that old graphical session and authenticate into the updated profile, or reboot, before treating recovery as protected. The systemd package hook reloads user managers for the installed service drop-in; deployment must still check the next session's effective ExecStart and that its MainPID is the guard. Do not call a live unguarded session migrated merely because the new files exist.

For rollback, first authenticate on a TTY and end the graphical session. Keep a root-owned copy of `session-guard-install.py` outside the package tree, restore both previous runtime/settings packages together, then run that saved script with `--rollback` to remove only the owned PAM line. The rollback API refuses while either guarded entry point remains installed; removing authenticated recovery first could strand a locked login. During restoration, a missing PAM helper denies graphical login until the saved rollback completes. Keep the TTY authenticated throughout, and do not launch graphical sessions during this maintenance. Do not delete a lock-intent marker to recover an unauthenticated desktop. If state permissions are invalid, authenticate on a TTY before repairing them.

Command tests cover queued replacements, compositor termination, first-exec denial, persistent intent with a fresh runtime directory, marker failures, authenticated versus autologin PAM dispatch, repeated setup and rollback. They do not establish that any particular compositor crash is fixed or replace physical suspend, greeter and password/fingerprint acceptance on the deployed versions.
